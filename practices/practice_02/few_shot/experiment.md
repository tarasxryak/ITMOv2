# Few-shot

Файл ведёт OpenCode по вашим запросам. Агент записывает фактические результаты экспериментов и вносит изменения в связанные файлы. Свою оценку сообщайте ему в чате; вручную заполнять шаблон не нужно.

- Артефакт Практики 1: practices/practice_01/problem.md - раздел "Метрики"
- Что хотим улучшить: формулировки продуктовых метрик с отсутствующей базой
  - "Медианное время работы ревьюера на один PR"
  - "Доля полезных комментариев помощника (приняты ревьюером)"

## Примеры

### Хороший результат

SEC-1: число секретов, дошедших до внешнего LLM | По коду: 100% уходят в LLM (review_service.py:14) | 0 | Непрерывно | Прод: счётчик срабатываний маскировки (без содержимого); Тесты: корпус с секретами

### Плохой результат

Медианное время работы ревьюера на один PR | Не измеряется | -20% | Ежемесячно | Опрос ревьюеров/трекер времени

## Запрос

Эксперимент 1 Практики 2, техника Few-shot. Работай только с practices/practice_02/few_shot/experiment.md — заполни его разделы по шаблону. Файлы Практики 1 пока НЕ меняй.

Вход: practices/practice_01/problem.md, таблица "Метрики".
Хороший пример (из того же файла, строка SEC-1): "SEC-1: число секретов, дошедших до внешнего LLM | По коду: 100% уходят в LLM (review_service.py:14) | 0 | Непрерывно | Прод: счётчик срабатываний маскировки (без содержимого); Тесты: корпус с секретами" — есть текущее значение с источником, цель, окно замера и способ получить данные.
Плохой пример (строка 15 того же файла): "Медианное время работы ревьюера на один PR | Не измеряется | -20% | Ежемесячно | Опрос ревьюеров/трекер времени" — цель в процентах от базы, которой нет, и процедура замера не описана.

Задача few-shot: по образцу хорошего примера предложи новые формулировки для двух продуктовых метрик — "Медианное время работы ревьюера на один PR" и "Доля полезных комментариев помощника (приняты ревьюером)". Каждая должна получить либо конкретную базу, либо описанную процедуру снятия базы до внедрения, окно замера и источник данных. Не выдумывай числа, которых нет в репозитории: если базы нет, предложи процедуру её снятия.

## Что получили

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---|---|---|---|
| Медианное время работы ревьюера на один PR | База: снять до внедрения - выгрузка таймштампов событий VCS по PR (review requested/created -> approved/merged); медиана по всем PR в периоде до запуска | -20% | Ежемесячно | Выгрузка API VCS: список PR с датами review_requested/created и approved/merged; оффлайн расчёт медианы (без содержимого PR) |
| Доля полезных комментариев помощника (приняты ревьюером) | База: снять в пилоте - для каждого комментария ассистента ревьюер ставит явную отметку "accepted" (реакция/тег) в PR; доля = принятые/все комментарии ассистента | ≥ 60% | Еженедельно | Отметки ревьюера в PR (реакции/теги) + журнал помощника с ID комментариев (без содержимого) |

## Что изменили в исходном артефакте

- Файл и раздел: practices/practice_01/problem.md, таблица «Метрики», первая строка + сноска под таблицей
- Изменение: строка «Медианное время работы ревьюера на один PR | Не измеряется | -20% | Ежемесячно | Опрос ревьюеров/трекер времени» заменена на «Медианное время ревью PR (прокси времени работы ревьюера) | База снимается до внедрения: медиана по выгрузке таймштампов PR (review_requested → approved/merged) за 4 недели | -20% к базе | Ежемесячно | API VCS: даты review_requested и approved/merged, без содержимого PR»; под таблицей добавлена прокси-оговорка про lead time
- Как проверили: make step1 проходит; в строке метрики есть база, окно замера и источник; название метрики совпадает с тем, что измеряет источник; сноска отделена от таблицы пустой строкой и не ломает рендер
- Что отклонили: источник «Опрос ревьюеров/трекер времени» — невоспроизводим и не даёт базы; переписывание второй продуктовой метрики («Доля полезных комментариев») в этом эксперименте — способ её замера выбираем отдельно техникой Tree of Thoughts, чтобы решение было обоснованным, а не первым попавшимся
