# Зачем нужны подключения

Каждое подключение стоит ради конкретного шага работы. Подтверждения применения собраны в [`evidence/summary.md`](evidence/summary.md).

| Подключение | Зачем | Какой шаг улучшило | Подтверждение |
|---|---|---|---|
| `AGENTS.md` | Правила проекта лежат в корне и подключаются к каждой сессии: где контракт, какая команда проверки, что нельзя менять и делать без поручения | Любая сессия: агент знает границы без пересказа и не коммитит сам | Сессия 01: агент назвал команду проверки и запреты. В сессиях 01–09 нет `git commit`, `git push` и вызовов закрытых tools |
| Skill `test-driven-development` | Заставляет писать падающий тест до кода | Парсер КБЖУ и скор (02), клиент ВкусВилла (03), свой MCP-сервер (04) | Вызов `Skill` в сессиях 02, 03, 04, 06, 07, 08, 09, красные запуски hook сменяются зелёными |
| Skill `frontend-design` | Требует план дизайна и проверку на шаблонность до кода | Интерфейс игры (08) | Вызов `Skill` в сессиях 08 и 09 |
| MCP `vkusvill` | Единственный источник реальных товаров, цен и КБЖУ: агент не выдумывает данные | Фикстуры для тестов из настоящих ответов (02, 03), проверка корзины | Вызовы `products_search`, `product_details`, `cart_link_create` в сессиях 01–03 |
| MCP `looksmax` (свой) | Агент проверяет данные теми же функциями, что использует игра: `score_product`, `build_round`, `judge_round` | Подбор запросов для раундов (06, 07), демо успеха и ошибок (05) | Сессия 05: вызовы с корректным и ошибочным входом |
| MCP `shadcn` | Исходники компонентов интерфейса берутся из первоисточника, а не по памяти модели | Новый интерфейс: кнопки, карточки, вкладки, диалоги | `evidence/shadcn-mcp.json`: 13 вызовов `get_component` |
| Hook `check-after-edit.sh` | После каждой правки запускает `scripts/check.sh` и возвращает результат агенту | Цикл «правка, проверка, исправление» без моего участия | Сводка по сессиям: в 02 сработал 31 раз, 18 красных и 13 зелёных |
