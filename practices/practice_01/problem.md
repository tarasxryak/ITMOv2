# Проблема и метрики

## Проблема

- Пользователь: ревьюер PR (человек); запрос может отправлять CI от его имени.
- Ситуация: добавлен эндпоинт POST /api/reviews и сервис ReviewService, который передает сырой diff в LLM без валидации, ограничений и обработки ошибок (по TRAINING_PR.diff).
- Что происходит сейчас: при отсутствии поля "diff" возможен KeyError (AS IS: 500); большие диффы не ограничены; таймауты LLM не обрабатываются; формат ответа свободный и не соответствует OUT-1.
- Почему это мешает пользователю или бизнесу: нестабильность ревью в пайплайне, простои, рост затрат на LLM, риски безопасности и утечки кода.
- Что не входит в задачу: разработка UI, глубокая интеграция с VCS (GitHub/GitLab) и настройка внешних провайдеров LLM.

## Метрики

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---|---|---|---|
| Медианное время работы ревьюера на один PR | Не измеряется | -20% | Ежемесячно | Опрос ревьюеров/трекер времени |
| Доля полезных комментариев помощника (приняты ревьюером) | Не измеряется | ≥ 60% | Еженедельно | Отметки ревьюера в PR |
| SEC-1: число секретов, дошедших до внешнего LLM | По коду: 100% уходят в LLM (review_service.py:14) | 0 | Непрерывно | Прод: счётчик срабатываний маскировки (без содержимого); Тесты: корпус с секретами |
| QA-1: доля рисков без подтверждения diff/правилом | Не измеряется | 0 | На каждом релизе | Прогоны на фиксированном наборе diff и/или отметки ревьюера |
| OUT-1: доля ответов, прошедших схему | По коду: 0% (review_service.py:16) | 100% | Непрерывно | Валидатор схемы |
| REL-1: доля ответов 500 при ошибке/timeout LLM | По коду: 100% (review_service.py:15) | 0; timeout → 504 с телом OUT-1 | Непрерывно | HTTP-логи/APM |

## Почему изменение метрики подтвердит решение проблемы

Снижение доли 500 при ошибке/timeout до 0 с одновременным появлением 504 с телом OUT-1 подтвердит корректную обработку REL-1. 100% соответствие OUT-1 гарантирует пригодность ответа для автоматической обработки. Нулевая доля секретов, уходящих во внешний LLM, подтверждает выполнение SEC-1. Нулевая доля неподтвержденных рисков подтверждает выполнение QA-1. Продуктовые метрики (медианное время и доля полезных комментариев) покажут ценность для ревьюера.

## Как использовали AI

- Для чего: формализовать проблему и метрики успеха по CASE.md.
- Тип промпта: master prompt.
- Строка в [`prompts.md`](prompts.md): P1-03 (генерация артефактов), P1-04 (доработка по ревью), P1-07 (аудит готовности).
- Что проверили и исправили сами: убрали противоречие «5xx → 0» с допущением REL-1 (504); замер SEC-1 перевели на счётчик срабатываний маскировки, а QA-1 — на прогоны фиксированного набора diff, чтобы не противоречить OBS-1; текущие значения SEC-1, OUT-1 и REL-1 взяли из кода со ссылками на строки.
