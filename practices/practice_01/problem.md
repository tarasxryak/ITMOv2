# Проблема и метрики

## Проблема

- Пользователь: ревьюер PR (человек) принимает решение; помощник только советует. (SCOPE-1)
- Ситуация: добавлен POST /api/reviews, вызывающий review_service.review(payload["diff"]). (TRAINING_PR.diff:37)
- Что происходит сейчас:
  - при отсутствии поля diff возникает KeyError; обработчика ошибок нет, поэтому ответ 500 (допущение: код ответа в диффе не задан) (TRAINING_PR.diff:37)
  - ограничение длины diff отсутствует: весь diff подставляется в prompt без проверок (TRAINING_PR.diff:20)
  - таймаут и обработка ошибок вызова LLM отсутствуют (TRAINING_PR.diff:21)
  - формат ответа свободный: возвращается comment с текстом LLM, не OUT-1 (TRAINING_PR.diff:22)
- Почему это мешает: нестабильность и простои пайплайна из-за необработанных исключений/таймаутов (REL-1); рост затрат на LLM при больших диффах без лимита (API-1); риски безопасности при отправке сырого diff во внешний LLM (SEC-1); ответ непригоден для автоматической обработки, не соответствует требуемой структуре (OUT-1).
- Что не входит в задачу: разработка UI, глубокая интеграция с VCS (GitHub/GitLab) и настройка внешних провайдеров LLM — допущение, в диффе и правилах этих требований нет. Границы помощника заданы отдельно: approve, merge и изменение кода выполняет человек (SCOPE-1)

## Метрики

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---|---|---|---|
| Медианное время ревью PR (прокси времени работы ревьюера) | База снимается до внедрения: медиана по выгрузке таймштампов PR (review_requested → approved/merged) за 4 недели | -20% к базе | Ежемесячно | API VCS: даты review_requested и approved/merged, без содержимого PR |
| Доля полезных комментариев помощника (приняты ревьюером) | База снимается в пилоте: ревьюер отвечает на комментарий помощника маркером ACCEPT или REJECT; доля = ACCEPT / все комментарии помощника | ≥ 60% | Еженедельно | API VCS: реплаи с маркером и ID комментариев помощника, без содержимого (OBS-1) |
| SEC-1: число секретов, дошедших до внешнего LLM | По коду: 100% уходят в LLM (review_service.py:14) | 0 | Непрерывно | Прод: счётчик срабатываний маскировки (без содержимого); Тесты: корпус с секретами |
| API-1: доля ответов 413 при diff > 20 000 символов | По коду: 0% — длина diff не проверяется, payload принимается как есть (api.py:8-10). | 100%; вызовов LLM при превышении лимита — 0 | Непрерывно | HTTP-логи; прогон проверок U-07, I-02, E-03 |
| OBS-1: доля логов, содержащих diff или ответ модели | Не определено: логирование в диффе отсутствует | 0 | Непрерывно | Аудит полей лога; прогон проверки I-04 |
| QA-1: доля рисков без подтверждения diff/правилом | База снимается прогоном на фиксированном наборе diff; доля = риски без evidence / все риски в ответе (допущение: состав набора в источниках не описан) | 0 | На каждом релизе | Отчёт прогона проверок U-06 (tests_unit.md) и I-05 (tests_integration.md) |
| OUT-1: доля ответов, прошедших схему | По коду: 0% (review_service.py:16) | 100% | Непрерывно | Валидатор схемы |
| REL-1: доля ответов 500 при ошибке/timeout LLM | По коду: 100% (review_service.py:15) | 0; timeout → 504 (допущение) с телом OUT-1 | Непрерывно | HTTP-логи/APM |

Прокси-оговорка: метрика времени измеряет lead time ревью PR, включая ожидание, а не только чистое время работы ревьюера; отдельного замера чистого времени в источниках нет.

Проверки метрик (трассировка — adr.md, раздел «Трассировка правил»): SEC-1 — U-01..U-03, I-01, E-02; API-1 — U-04, U-07, I-02, L-03, E-03, E-05; OBS-1 — I-04; OUT-1 — U-06, I-05, E-01; REL-1 — U-05, I-03, L-01, L-02, E-04; QA-1 — U-06, I-05. Продуктовые метрики (время ревью и доля полезных комментариев) тестами не покрываются: в tests_*.md проверок для них нет.

## Почему изменение метрики подтвердит решение проблемы

Снижение доли 500 при ошибке/timeout до 0 с одновременным появлением 504 (допущение) с телом OUT-1 подтвердит корректную обработку REL-1. 100% соответствие OUT-1 гарантирует пригодность ответа для автоматической обработки. Нулевая доля секретов, уходящих во внешний LLM, подтверждает выполнение SEC-1. Нулевая доля неподтверждённых рисков на фиксированном наборе diff подтверждает выполнение QA-1 в пределах этого набора; на произвольном трафике метрика не замеряется. Продуктовые метрики (медианное время и доля полезных комментариев) покажут ценность для ревьюера.
