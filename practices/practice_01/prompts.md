## Master Prompt v1

Соберите здесь контракт второго запуска. Не копируйте все документы целиком — ставьте ссылки на файлы и переносите только необходимый для задачи контекст.

### 1. Цель и роль

- Цель: провести структурированное ревью PR-диффа и выделить проверяемые риски с конкретными ссылками на строки.
- Роль AI: AI-Reviewer, соблюдающий границы и дающий evidence + check для каждого риска.

### 2. Входы и источники

- Обязательный вход: файл TRAINING_PR.diff.
- Разрешённые файлы и источники: только содержимое диффа и файлы практики 1 — `context.md`, `problem.md`, раздел P1-01 в этом файле.
- Context Pack — факты, правила, примеры и ограничения: см. `practices/practice_01/context.md`.

### 3. Задача и артефакты

- Что сделать: проанализировать дифф, выделить риски/уязвимости, сопроводить каждый пункт evidence и шагами проверки.
- Что вернуть: краткое summary + минимум 3 риска, каждый с evidence и check. Если нет evidence — пропустить.

### 4. Формат результата

- Структура ответа: раздел «Краткое резюме», далее список рисков. Для каждого риска: candidate, evidence (цитаты с файлами и строками), check (пошаговые действия).
- Ограничения объёма: до 600 слов, без скрытой CoT, только проверяемые утверждения.

### 5. Полномочия и запреты

- Разрешено: делать выводы по диффу; указывать воспроизводимые проверки; ссылаться на конкретные строки.
- Запрещено: придумывать несуществующие файлы/поведение; давать неподтвержденные утверждения; раскрывать CoT.

### 6. Рабочий процесс и остановка

- Шаги: прочитать дифф; сформировать summary; собрать риски; на каждый риск найти evidence и описать check; выполнить финальную валидацию ссылок.
- Когда остановиться и запросить человека: если требуется продуктовая политика (auth), конкретные шаблоны маскировки секретов, HTTP-коды при таймауте — см. «Что пока неизвестно» в context.md.

### 7. Проверки и evidence

- Как проверять утверждения: через локальные вызовы API, моки LLM, нагрузочные тесты; ссылки на строки диффа обязательны.
- Какое evidence сохранить: выдержки из диффа с номерами строк и файлами, команды для воспроизведения.

### 8. Definition of Done

- Задача закончена, когда: есть summary и ≥3 риска; каждый риск имеет evidence и check; ссылки валидны; нет неподтвержденных утверждений.

### P1-01 Результат

Ниже — ревью PR с акцентом на риски, возможные баги и пропуски в валидации/тестах. Ссылки даю по файлам и строкам из диффа.

Findings (по убыванию критичности)
1) Некорректная обработка входных данных и ошибки вместо 422
- app/api.py:8-10. Эндпоинт принимает произвольный dict и делает payload["diff"]. При отсутствии ключа или неверном типе будет KeyError и 500, вместо 422 с пояснением. Нет схемы запроса/ответа.
- Рекомендация: ввести Pydantic-модель запроса с обязательным полем diff и response_model для ответа. Пример: class ReviewRequest(BaseModel): diff: str. В обработчике использовать типизацию через модель.

2) Отсутствие обработки ошибок при обращении к LLM
- app/review_service.py:13-16 и app/api.py:8-10. Любая ошибка LLM (таймаут, сетевой сбой, лимиты) приведет к 500 без контролируемого ответа/логирования.
- Рекомендация: оборачивать вызов llm.generate в try/except и маппить ошибки на понятные статусы (например, 503 Service Unavailable), логировать исключения.

3) Риск переполнения контекста LLM и непредсказуемые отказы
- app/review_service.py:13-16. В prompt без ограничений подставляется весь diff. Крупные PR могут превышать лимит контекста или резко удорожать/замедлять вызов.
- Рекомендация: ввести ограничения на размер diff, чанкинг с агрегированием результатов, тримминг, эвристику (например, анализ только измененных участков по файлам, верхние N кБ).

4) Потенциальные проблемы DI и тестируемости из-за синглтона review_service
- app/api.py:8-10. Глобальный импорт review_service вместо Depends. Это усложняет тестирование, может порождать зависимости времени импорта и циклы, и мешает конфигурировать разные реализации LLM на окружениях.
- Рекомендация: использовать FastAPI Depends для внедрения сервиса или провайдера, либо фабрику приложения, где зависимости прокидываются явно.

5) Безопасность и приватность данных
- app/review_service.py:13-16. В LLM уходит сырой diff без маскировки секретов/PII и без защиты от prompt injection (пользовательский контент может навязать инструкции).
- Рекомендация: а) фильтровать/маскировать секреты, b) добавлять жесткий system prompt с правилами, c) экранировать/нормализовать пользовательский текст, d) при внешнем LLM — убедиться в согласованных политиках/договоренностях.

6) Отсутствие аутентификации/авторизации на write-эндпоинте
- app/api.py:8-10. POST /api/reviews доступен без ограничений. Если сервис публичный, это приводит к злоупотреблениям, затратам и утечке кода в LLM.
- Рекомендация: ввести auth и/или rate limiting, quota, Captcha по контексту продукта.

7) Нестабильность/неопределенность формата ответа от LLM
- app/review_service.py:13-16. Промпт слишком общий ("Review this pull request and find problems"). Нет указания формата (ссылки на файлы/строки, уровень критичности, структура). В итоге ответ может быть «водянистым» и труднопарсируемым.
- Рекомендация: задать четкий, детерминированный промпт: требовать список находок c полями: severity, file, line, message; формат JSON; лимит пунктов; правила сортировки и примеры.

8) Блокирующий вызов LLM в синхронном обработчике
- app/api.py:8-10. Эндпоинт синхронный, вызов LLM может быть долгим и блокировать воркер. При Uvicorn/ Gunicorn это ограничивает RPS.
- Рекомендация: либо сделать endpoint async и вынести блокирующий вызов в threadpool (run_in_executor), либо организовать очередь/фоновые задания.

9) Нет логирования и трассировки
- Ни в сервисе, ни в API не логируются входы/ошибки/время ответа LLM. Тяжело отлаживать и мониторить.
- Рекомендация: добавить структурное логирование, метрики времени и исходов (успех/ошибка).

10) Отсутствуют тесты
- Нет unit-тестов на ReviewService.review (мок LLM), нет тестов API с валидацией и ошибками. Риск регрессий.
- Рекомендация: добавить тесты на happy-path, отсутствие diff, слишком длинный diff, таймаут LLM.

11) Мелочи стиля/качества
- app/review_service.py:9-13. Переформатирован Protocol метод без изменения логики; не несет пользы.
- Возврат через словарь dict[str, str] как контракт лучше заменить на Pydantic модель для стабильного API и документации.
- Возможна несогласованность языка: промпт на английском, контекст/задача — на русском. Лучше единообразно.

Открытые вопросы
1) Какой ожидаемый контракт ответа? Нужны ли severity, ссылки на файл/строки, типы проблем, формат JSON?
2) Максимальный допустимый размер diff и поведение при превышении (отрезать, чанковать, отдавать 413 Payload Too Large)?

4) Должен ли /api/reviews быть защищен и как (auth, роли, rate limit)?
5) Нужны ли асинхронность/очереди или достаточно sync при целевых нагрузках?

### Разбор P1-01

- Краткий результат: модель выдала 11 находок, 5 открытых вопросов и список из 6 рекомендаций. Реальные дефекты диффа найдены — `KeyError` на `payload["diff"]`, отсутствие таймаута и обработки ошибок LLM, неограниченный размер диффа, сырой diff во внешний LLM, свободный формат ответа, отсутствие логов и тестов. Всё это вперемешку с требованиями, которых в кейсе нет.
- Слабые места ответа (3):
  1. Нет воспроизводимых проверок. На каждый риск даётся «Рекомендация» — что дописать в код, а не как убедиться, что риск реален: «Рекомендация: ввести Pydantic-модель запроса с обязательным полем diff». Проверить утверждение по такому ответу нельзя.
