## Context Pack для первого рабочего сценария

### Факты и правила

- app/api.py:8-10 — синхронный эндпоинт POST /api/reviews принимает payload: dict.
- app/api.py:10 — вызывается review_service.review(payload["diff"]). Нет проверки наличия поля и длины; при отсутствии поля — KeyError и 500.
- app/review_service.py:14 — diff целиком подставляется в prompt, без удаления секретов и без лимита.
- app/review_service.py:15 — self.llm.generate(prompt) — без timeout и обработки ошибок.
- app/review_service.py:16 — возвращается {"comment": answer} — свободный текст, не OUT-1. Риски не фильтруются.
- Логирования в diff нет.
- SEC-1: перед отправкой во внешний LLM из diff удаляются токены, пароли и приватные ключи.
- API-1: diff длиннее 20 000 символов отклоняется с HTTP 413.
- REL-1: внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ.
- OUT-1: ответ содержит summary, массив risks и массив checks. В risks максимум три элемента с полями file, line, evidence, risk.
- SCOPE-1: сервис только советует; он не пишет код и не выполняет действия в GitHub.
- QA-1: риск включается в ответ, только если он подтверждён строкой diff или правилом репозитория.
- OBS-1: в лог пишутся только request_id, длительность и статус. Содержимое diff и ответа модели не логируется.

### Формат входа и результата

- Вход: JSON { "diff": string } — наличие и тип значения diff не проверяются в текущем коде.
- Выход: { "comment": string } — свободный текст из LLM; целевое требование по OUT-1: summary + risks[] + checks[].

### Ограничения и запрещённые действия

- SEC-1: секреты маскируются перед вызовом LLM.
- API-1: диффы > 20 000 символов отклоняются с 413; проверка длины выполняется до маскировки и до вызова LLM.
- REL-1: на внешние вызовы действует таймаут 10 секунд; ошибка конвертируется в контролируемый ответ.
- OUT-1: структура ответа фиксирована; рисков не больше трёх.
- QA-1: в финальный ответ попадают только риски, подтверждённые строкой diff или правилом.
- OBS-1: не логировать содержимое входных данных и ответа модели.
- SCOPE-1: помощник не может approve, merge или менять код и действовать в GitHub; решение принимает человек.

### Хороший пример
Источник: CASE.md.

```text
app/review_service.py:16 — diff отправляется во внешний LLM без удаления секретов,
что нарушает SEC-1. Проверка: передать diff с тестовым token и убедиться,
что в prompt осталось [REDACTED].
```
Пояснение: в CASE.md указана :16; по нумерации новой версии вызов LLM находится на :15.

### Плохой пример
Источник: CASE.md.

```text
Код можно улучшить. Добавьте тесты и обработку ошибок.
```

### Что пока неизвестно

- HTTP-код и тело ответа при timeout внешнего LLM. Допущение: HTTP 504, тело в формате OUT-1 с summary об ошибке и пустыми risks и checks.
- Способ поиска и маскировки секретов (точные шаблоны: токены, пароли, приватные ключи).
- Конкретный LLM-провайдер и политика обработки данных.
- Замечание: правила про snake_case и i18n не включены, так как не относятся к учебному PR (CASE.md).

## Как использовали AI

- Для чего: зафиксировать контекст, правила и неизвестное для сценария помощника ревьюера PR.
- Тип промпта: master prompt.
- Строка в [`prompts.md`](prompts.md): P1-03 (генерация артефактов), P1-04 (доработка по ревью), P1-07 (аудит готовности).
- Что проверили и исправили сами: сверили 7 правил и оба примера с CASE.md дословно; убрали из примеров придуманные требования (auth, SLA); убрали из «Что пока неизвестно» лимит diff и формат ответа — их задают API-1 и OUT-1; к примеру из CASE.md со ссылкой `:16` добавили пояснение, что вызов LLM находится на `:15`; источник «CI» пометили как допущение.
